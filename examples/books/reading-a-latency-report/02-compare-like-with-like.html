2 - Compare like with like

On Monday, the museum website recorded a p95 of 80 milliseconds. On Tuesday, it recorded 400 milliseconds. Before asking what changed in the website, check what changed in the requests.

Compare the traffic mix

For this example, assume that every request to browse exhibitions takes 80 milliseconds and every request to buy a tour ticket takes 400 milliseconds. Both days have one hundred requests. Only the traffic mix changes.

The 95th request in order is a browse request on Monday and a ticket purchase on Tuesday. Both activities take the same time as before. The overall percentile rises because ticket purchases make up a larger share of the requests.

Break down the results

Calculate response times separately for browsing and buying. Each activity has the same p95 on both days, which explains the apparent slowdown in the overall report. In a real report, include the number of requests behind each figure. Four purchases on Monday give very little evidence about how buying works when the museum is busy.

It can also help to look at changes within an activity. A longer response time for ticket purchases might affect all purchases, or it might be limited to a particular tour. The right breakdown depends on the question you are trying to answer.

Match the measurement

Check where each timer starts and stops. A browser can measure how long the visitor waits, including the connection to the website. A timer on the server can start after the request arrives and stop before the response reaches the visitor. Both numbers describe time spent waiting, but they cover different parts of the trip.

When comparing reports, use the same definition of a request, the same units, and the same start and end points. If you are deciding whether a recent change slowed down purchases, compare measurements for purchases taken under similar conditions.
