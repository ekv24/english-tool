# Рекомендации чтения: читалка как оболочка личной системы

Triage: ready-for-agent

## Часть 1. Решения

### Проблема и результат

Я читаю статьи и книги в English Tool, пишу агенту отзывы и задаю вопросы о прочитанном. Нужно, чтобы система запоминала эти сигналы и со временем оценивала, насколько мне будет интересен новый материал, а затем сама находила подходящие статьи и книги. Читалка становится видимой частью системы. В ней я читаю, отвечаю на короткий вопрос о материале и вижу, что мне предлагают. Агенты (Claude Code, Codex) работают с теми же данными через API читалки.

### Что сделано в первой итерации (2026-11-22)

1. **Сигналы чтения.** Для каждого документа читалка считает за день активное время чтения и число поисков слов. Время идёт, пока страница видна и в последние 90 секунд была прокрутка, касание или ввод. Эти данные синхронизируются между устройствами, как позиции и словарь.
2. **Your take.** В конце каждой статьи и главы, а также на странице книги, есть карточка из двух вопросов: интерес (More like this / It was fine / Not for me) и трудность английского (Easy / Just right / Hard). К ним можно добавить заметку. Отзыв относится к материалу целиком, а для книг — ко всей книге.
3. **Журнал.** Агент записывает сказанное в чате: отзывы, вопросы, интересы. Если запись относится к материалу, она к нему привязана.
4. **For you.** Библиотека показывает предложения агента с причиной выбора. Предложение можно отметить **Want to read** или скрыть через **Not interested**. Оба выбора тоже служат сигналами.
5. **Интерфейс для агентов.** `GET /api/library` отдаёт каталог (названия, источники, длину страниц), а существующий `POST /api/reader-state` возвращает и принимает записи. `npm run interests -- <команда>` собирает из них дайджест и записывает заметки, предложения и профиль.
6. **Правила для агентов.** Инструкции лежат в [AGENTS.md](../../AGENTS.md) и [docs/agents/recommendations.md](../agents/recommendations.md), скиллы — в `.agents/skills/`. Там описано, когда записывать отзыв из чата и как делать подбор.

### Критерии приёмки

- Отзыв, оставленный на одном устройстве, виден на другом и попадает в дайджест.
- Время чтения и поиски появляются в дайджесте по материалу. Простой без активности не засчитывается.
- `note`, `suggest`, `imported`, `profile` и `forget` меняют данные живой читалки, и это видно в дайджесте.
- Предложение агента появляется в **For you**. **Not interested** скрывает его после перезагрузки, **Want to read** поднимает выше и подсказывает следующий шаг.
- В репозитории нет личных данных. Тесты используют синтетические записи.
- Все проверки проходят: `npm run check`, `npm test`, `npm run test:browser`.

### Границы и ограничения

- **Личные данные хранятся только в базе читалки** в каталоге данных (`.local/` или `ENGLISH_TOOL_DATA_DIR`). Репозиторий публичный, поэтому в git попадают код, форматы и процедуры, но не журнал, профиль и дайджест. См. [ADR 0001](../adr/0001-reader-data-and-agent-api.md).
- **Модель не обучается.** Оценку и поиск делает агент по дайджесту и профилю интересов. Один читатель и десятки материалов — слишком мало данных для статистической модели.
- **Книги агент не скачивает.** Для книги предложение означает «найди экземпляр». Статьи из открытых источников агент может подготовить сам.
- **Читалка ничего не ищет сама.** Сайт показывает данные и собирает ответы. Подбор выполняет агент по запросу.

### Критика идеи и как она учтена

- **Интерес и трудность — разные оси.** Медленное чтение или брошенный текст могут означать, что английский слишком трудный, а не что тема скучная. Поэтому в отзыве два отдельных вопроса, а плотность поисков на 1000 прочитанных слов служит грубой мерой трудности.
- **Неявные сигналы шумные.** Время и прогресс зависят от длины, настроения и устройства. Главный сигнал — явный ответ в **Your take**, поэтому он стоит на виду и требует одного касания.
- **Отзыв в чате теряется без процедуры.** Записывать его в журнал обязаны все агенты. Правило вынесено в AGENTS.md.
- **Пузырь интересов.** Подбор оставляет одно место из пяти для темы за пределами профиля. **Not interested** — полезный сигнал, а не ошибка.
- **Сначала данные, потом автоматизация.** Регулярный подбор по расписанию и метрики качества имеет смысл вводить после нескольких ручных проходов. Карточки для этого заведены.

### Открытые решения (пока действуют предложения по умолчанию)

1. **Частота подбора.** По умолчанию подбор запускается по просьбе: «подбери, что почитать». Расписание (например, раз в неделю) — [№07](../../.scratch/reading-recommendations/issues/07-scheduled-recommendations.md).
2. **Источники поиска.** По умолчанию поиск начинается с источников и авторов понравившихся материалов, затем идёт общий веб-поиск. Список любимых источников можно дописать в профиль.
3. **Самостоятельная подготовка.** По умолчанию статью, отмеченную **Want to read**, агент готовит без отдельного вопроса. Для книги сначала нужен файл от пользователя.

## Часть 2. Детали исполнения

### Записи состояния

Все сигналы — записи `[key, updatedAt, value]` в таблице `reader_state`. При конфликте побеждает более позднее изменение. Проверка формата находится в [public/reader-records.js](../../public/reader-records.js) и общая для сервера, браузера и CLI. Документ — это статья `<id>` или страница книги `<book>/<slug>`.

| Ключ | Значение | Кто пишет |
| --- | --- | --- |
| `activity:<document>:<yyyy-mm-dd>` | `{seconds, lookups}`, целые, за локальный день | сайт |
| `feedback:<material>` | `{interest?, level?, note?}`; `{}` после очистки | сайт |
| `note:<id>` | `{text, kind, source, at, material?}`; `kind`: feedback, question, interest или note; `source`: site, chat или agent; `null` после удаления | агент |
| `suggestion:<id>` | `{title, url, kind, why, score, addedAt, author?, publisher?, minutes?, level?, material?}`; `score` — оценка вероятности «More like this»; `material` появляется после подготовки | агент |
| `choice:<id>` | `want`, `dismissed` или `null` | сайт |
| `profile:interests` | `{text}` — Markdown до 32 000 знаков | агент |

Если `isReaderRecord` начинает принимать новый вид записей, нужно поднять `recordSchema`. Тогда браузеры заново запросят записи, которые раньше пропустили.

### Синхронизация и скорость

Браузер хранит последнюю ревизию и эпоху базы (`reader-state:revision`) и при следующей загрузке страницы запрашивает только изменения после неё. Раньше каждая страница скачивала всё состояние заново: около 90 КБ при 200 словах, и объём рос со словарём. У базы есть случайная эпоха в `reader_meta`. Восстановленная из резервной копии база получает новую эпоху, и браузеры запрашивают всё заново. Ответы API больше 1 КБ сжимаются br или gzip.

### API и CLI

- `GET /api/library` возвращает `{articles:[{id,title,publisher,kind,date,source,words}], books:[{id,title,author,description,source,pages:[{slug,title,type,words}]}]}`. Данных читателя в ответе нет.
- `POST /api/reader-state` с `{since:0, records:[]}` возвращает всё состояние. Новые записи передаются в `records`.
- `scripts/interests.mjs` (`npm run interests -- --help`) по умолчанию обращается к `http://127.0.0.1:4173`. Адрес меняется через `--server` или `ENGLISH_TOOL_URL`. Команды: `digest [--json]`, `note`, `suggest`, `imported`, `profile [--set file|-]`, `forget`. Запись отклоняется, если в базе уже есть более новая версия ключа.

### Подбор (процедура агента)

Подробно описан в [docs/agents/recommendations.md](../agents/recommendations.md):

1. Прочитать дайджест.
2. Обновить профиль: темы, авторы и источники, уровень английского, предпочтительная длина, что не нравится.
3. Найти кандидатов. Одно место из пяти отдать новой теме.
4. Оценить `score` и записать `why` со ссылкой на конкретные сигналы.
5. Добавить не больше пяти предложений. Скрытые повторно не предлагать.
