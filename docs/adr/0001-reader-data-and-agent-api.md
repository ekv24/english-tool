# 0001. Личные данные живут в базе читалки, агенты работают через её API

Дата: 2026-11-22. Статус: принято.

## Контекст

Читалка становится оболочкой личной системы рекомендаций. Сигналы приходят с сайта: позиции, словарь, отзывы, время чтения. Другие сигналы приходят из чатов с агентами: впечатления, вопросы, интересы. Данные читаются с нескольких устройств. Репозиторий публичный, и в git не должно попадать ничего личного. Агенты запускаются в той же папке, что и код, и могут случайно записать журнал в файл под контролем версий.

## Решение

1. Все личные сигналы хранятся записями в базе читалки (`reader-state/reader.sqlite` в каталоге данных): позиции, отметки, выражения, активность, отзывы, журнал, профиль, предложения и выбор. Отдельных файлов с личными данными в репозитории нет.
2. Агенты читают и пишут только через HTTP API запущенной читалки (`/api/library`, `/api/reader-state`) с помощью `scripts/interests.mjs`. Напрямую SQLite агенты не меняют: так запись проходит ту же проверку, получает ревизию и сразу попадает в браузеры.
3. Запись — пара ключ-значение. При конфликте побеждает более позднее изменение. Формат каждого вида проверяет `public/reader-records.js`. Новый вид записей повышает `recordSchema`.
4. На этом этапе нет обучаемой модели. Оценку интереса делает агент по дайджесту и профилю. Модель или эмбеддинги имеют смысл, когда данных станет на порядок больше.

## Последствия

- Резервная копия каталога данных сохраняет всё, что система знает о читателе.
- Для работы агента читалка должна быть запущена. Если читалка недоступна, CLI сообщает об этом и ничего не пишет.
- Журнал и профиль синхронизируются в браузеры. Поэтому их размер ограничен: заметка до 4000 знаков, профиль до 32 000.
- Проверки агентов против рабочей читалки меняют настоящие данные. Для экспериментов нужен отдельный сервер и `--server`.
